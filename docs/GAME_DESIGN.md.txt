# РОДИНА — GAME DESIGN DOCUMENT

## 1. Общая информация

**Название проекта:** Родина  
**Жанр:** сюжетная 3D-игра от первого лица с элементами экшена, исследования и кинематографических сцен.  
**Движок:** Godot  
**Основной язык:** GDScript  
**Платформа:** PC  
**Сеттинг:** СССР, Великая Отечественная война.  
**Главный герой:** Дмитрий.

Игра строится вокруг линейного сюжетного прохождения. Основной акцент — атмосфера, ощущение присутствия, окружение, сюжетные события и отдельные запоминающиеся игровые эпизоды.

Проект должен восприниматься как единая история, а не как набор независимых уровней.

---

# 2. Основная концепция

Игрок управляет Дмитрием и проходит через последовательность событий военного времени.

Игра должна сочетать:

- исследование окружения;
- перемещение по локациям;
- взаимодействие с предметами и объектами;
- сюжетные события;
- разговоры и NPC;
- использование оружия;
- кинематографические сцены;
- напряжённые боевые эпизоды;
- атмосферное окружение;
- постепенное развитие истории.

Приоритет проекта:

1. Атмосфера и погружение.
2. Понятная и последовательная история.
3. Качественные локации.
4. Хорошее ощущение присутствия игрока в мире.
5. Надёжная работа игровых механик.
6. Качественные модели, материалы, освещение и звук.
7. Стабильность проекта.

Не следует добавлять механику только ради количества механик.

---

# 3. Главный герой

## Дмитрий

Дмитрий — главный управляемый персонаж игры.

Игрок должен воспринимать происходящие события преимущественно через него.

Дмитрий должен иметь:

- модель персонажа;
- корректный скелет/риг;
- анимации;
- систему перемещения;
- взаимодействия;
- возможность использовать оружие;
- возможность участвовать в сюжетных сценах;
- корректное размещение в транспорте и других объектах.

В будущих сценах модель Дмитрия должна быть пригодна для использования повторно.

Общий визуальный стиль:

- правдоподобные пропорции;

Особое внимание:

- грязи;
- камню;
- тканям;
- бетону;
- кирпичу;
- старой краске;
- следам эксплуатации.

Мир не должен выглядеть стерильно новым.

Предметы должны иметь признаки использования:

- грязь;
- потёртости;
- повреждения;
- пыль;
- следы ремонта;
- неровности;

# 5. Принцип работы с ассетами

Все игровые ассеты должны храниться локально в проекте.

Нельзя использовать внешние URL как источник игровых текстур, моделей или других ресурсов.

Предпочтительный формат 3D-моделей:

- GLB;
- GLTF.

Другие форматы допускаются как исходники, если требуется конвертация.

Оригинальные исходные файлы нельзя удалять без необходимости.

Особенно важно сохранять исходники при работе с нестандартными форматами.

Пример:

MDX/BLP → сначала сохранить оригиналы → выполнить анализ → при необходимости конвертировать → получить пригодный для Godot ресурс.

# 7. Глава 1

Глава 1 — первая полноценная игровая часть проекта.

Она должна быть законченной игровой последовательностью, а не техническим прототипом.

## Основные элементы

В главе присутствуют:

- военный лагерь/военная территория;
- жилые и служебные помещения;
- казармы;
- оружейная;
- двор;
- различные хозяйственные объекты;
- NPC;
- старший по званию;
- оружие;
- транспорт;
- различные мелкие предметы окружения.

Игрок должен иметь возможность нормально перемещаться по локации и взаимодействовать с предусмотренными объектами.

---

# 8. Старший по званию

В проекте существует NPC, являющийся старшим по званию.

Для него предусмотрена отдельная модель.

Модель старшего по званию может иметь нестандартный исходный формат, например MDX/BLP.

При интеграции необходимо:

1. сохранить оригиналы;
2. определить структуру модели;
3. проверить текстуры;
4. определить возможные анимации;
5. при необходимости выполнить конвертацию;
6. подключить материалы;
7. проверить масштаб;
8. проверить ориентацию;
9. заменить временную модель NPC;
10. сохранить существующую логику NPC.

Замена модели не должна ломать:

- диалоги;
- триггеры;
- взаимодействия;
- положение NPC;
- сюжетную последовательность.

---

# 9. Оружейная

В первой главе существует оружейная.

В ней используется локальное изображение/текстура, являющаяся частью оформления помещения.

Изображение должно:

- находиться внутри помещения;
- корректно отображаться;
- использовать локальный ресурс проекта;
- не загружаться через интернет;
- не превращаться в белый прямоугольник;
- быть корректно импортировано Godot;
- иметь правильный масштаб и ориентацию.

Если ресурс заменяется, необходимо сохранять фактическое изображение, а не создавать временную белую заглушку.

---

# 10. Транспорт

В игре используется советский грузовик ZiS-5.

Текущая модель:

`assets/vehicles/zis_5v/`

Предпочтительное расположение основной модели:

`assets/vehicles/zis_5v/zis_5v.glb`

ZiS-5 используется в первой главе и должен быть пригоден для дальнейшего использования во второй главе.

Важно:

**Текущий небольшой визуальный дефект — грузовик немного находится выше поверхности земли.**

Этот дефект существует и должен быть исправлен отдельной задачей.

При выполнении других задач нельзя случайно изменять положение ZiS-5 относительно земли без необходимости.

---

# 11. Глава 2 — общая задумка

Глава 2 будет представлять собой масштабную погоню.

Дмитрий находится в кузове ZiS-5.

Грузовик движется по лесной дороге.

Игрок управляет Дмитрием, но не грузовиком.

Грузовиком управляет NPC/система транспорта.

---

# 12. Начало погони

Грузовик движется по лесной дороге.

Впереди находится поворот.

Из-за поворота внезапно появляется немецкий танк Pz.III.

Появление должно быть резким и неожиданным.

Предпочтительный визуальный эффект:

- танк появляется из-за поворота;
- выходит на основную дорогу;
- появляется практически боком;
- после чего начинается преследование.

Pz.III — единственный преследующий танк.

Другие танки в этой погоне не нужны.

---

# 13. Pz.III

Pz.III является главным противником второй главы.

Танк должен иметь:

- корпус;
- башню;
- пушку;
- гусеницы;
- ходовую;
- левую гусеницу;
- правую гусеницу;
- другие внешние детали.

Основная игровая механика погони связана с повреждением гусениц.

---

# 14. Главная механика погони

Условие победы:

**Игрок должен вывести из строя гусеницу танка.**

Попадания в корпус сами по себе не должны завершать погоню.

Необходимо учитывать отдельно:

- левую гусеницу;
- правую гусеницу.

Повреждение гусениц может влиять на поведение танка.

Например:

- ухудшение поворота;
- изменение скорости;
- занос;
- визуальное повреждение;
- остановка после полного уничтожения необходимой гусеницы.

Игрок должен постепенно понимать, что гусеницы являются уязвимой частью танка.

Не обязательно давать прямую подсказку в виде текста.

---

# 15. Динамика погони

Погоня должна ощущаться динамичной.

Если игрок хорошо стреляет:

- танк отстаёт;
- расстояние увеличивается;
- напряжение постепенно меняется.

Если игрок стреляет плохо:

- танк приближается;
- опасность увеличивается.

Таким образом, расстояние между ZiS-5 и Pz.III является частью игровой системы.

---

# 16. Движение ZiS-5

ZiS-5 не обязан использовать полноценную реалистичную физическую модель автомобиля.

Для сюжетной погони предпочтительно использовать контролируемое движение по заранее подготовленному маршруту.

Грузовик должен:

- ускоряться;
- замедляться;
- проходить повороты;
- немного раскачиваться;
- наклоняться;
- подпрыгивать;
- реагировать на неровности;
- иногда смещаться влево/вправо;
- создавать ощущение высокой скорости.

Движение должно выглядеть убедительно, даже если технически оно является скриптовым.

---

# 17. Маршрут погони

Основная дорога должна быть заранее спроектирована.

Предпочтительно использовать заранее подготовленный маршрут, а не полностью случайную генерацию дороги.

В маршруте могут присутствовать:

- S-образные участки;
- резкие повороты;
- подъёмы;
- спуски;
- узкие участки;
- мост;
- грязь;
- лужи;
- неровности;
- следы техники;
- камни;
- препятствия;
- участки с ограниченной видимостью.

Продолжительность основной погони:

**примерно 5 минут.**

---

# 18. Лес

Лес должен окружать дорогу и создавать ощущение большой территории.

Не требуется вручную моделировать каждый объект леса.

Допускается процедурное размещение:

- деревьев;
- кустов;
- травы;
- камней;
- веток;
- пней;
- корней;
- сухой растительности.

При этом основной маршрут дороги должен оставаться контролируемым и заранее спроектированным.

---

# 19. Дмитрий в кузове

Во время погони Дмитрий находится в кузове ZiS-5.

Он сидит на краю кузова.

Игрок:

- не может свободно ходить по кузову;
- управляет только Дмитрием;
- может стрелять вокруг себя;
- может поворачиваться примерно на 360°;
- должен иметь удобную камеру для стрельбы.

Положение Дмитрия должно быть связано с отдельной точкой/anchor внутри грузовика.

Предпочтительная структура:

```text
ZiS5
├── VehicleBody
├── Wheels
├── CargoBed
├── PlayerSeat
│   └── Dmitry
├── CameraAnchor
└── ...
```

Это позволяет заменять модель грузовика без необходимости полностью переписывать систему размещения Дмитрия.

---

# 20. PPSh

В проекте используется пистолет-пулемёт ППШ.

Модель должна быть пригодна для:

- первой главы;
- второй главы;
- стрельбы;
- перезарядки;
- отображения в руках;
- корректного положения относительно камеры.

При замене модели оружия необходимо сохранить существующую игровую логику.

Нужно проверить:

- масштаб;
- направление ствола;
- положение относительно рук;
- положение относительно камеры;
- точку выстрела;
- анимации;
- перезарядку.

- камни;

- двери;

Временные модели постепенно заменяются финальными ассетами.

Замена должна сохранять:

- расположение;

# 22. Кампания и сюжет

Игра должна оставаться последовательной.

Каждая глава должна продолжать события предыдущей.

Не следует создавать механики или сцены, которые противоречат уже существующей задумке.

Если новая задача не определяет конкретное поведение, предпочтительно:

1. сохранить существующее поведение;
2. не добавлять новую механику без необходимости;
3. не ломать существующие системы;
4. сообщить о неоднозначности, если она действительно мешает реализации.

# 25. Правило временных ассетов

Временные модели разрешены на этапе разработки.

Но они должны постепенно заменяться финальными.

При замене:

- не ломать систему;
- не менять механику без необходимости;
- сохранять точки взаимодействия;
- сохранять коллизии;
- сохранять масштаб сцены;
- проверять ориентацию.

---

# 26. Масштаб

Все новые модели должны проверяться относительно существующего мира.

Особенно важно проверять:

- рост человека;
- высоту дверей;
- высоту столов;
- размер ящиков;
- размер бочек;
- размеры транспорта;
- размеры зданий;
- размеры оружия.

Нельзя просто импортировать модель и считать задачу выполненной.

---

# 27. Коллизии

Игровые коллизии должны быть проверены после замены моделей.

Особенно:

- двери;
- здания;
- стены;
- ящики;
- бочки;
- транспорт;
- крупные камни;
- элементы окружения.

Коллизии не должны:

- блокировать игрока без причины;
- позволять проходить сквозь стены;
- создавать невидимые стены;
- мешать взаимодействиям.

---

# 28. Принцип сохранения существующей логики

При работе над ассетами:

**модель не должна диктовать изменение игровой логики, если этого можно избежать.**

Если необходимо заменить модель:

> заменить визуальную часть → адаптировать transform/scale/collision → проверить существующую логику.

Не:

> заменить модель → переписать половину проекта.

Общие системы желательно делать переиспользуемыми:

- Player;
- Weapon;
- NPC;
- Interaction;
- Trigger;
- Vehicle;
- Audio;
- VFX;
- Camera;
- Save/Load;
- Scene transition.

Глава должна использовать общие системы, а не создавать отдельную копию каждой системы.

---

# 33. Главное правило

«Родина» должна ощущаться как одна цельная игра.

Любое техническое решение должно по возможности одновременно:

- сохранять текущую работоспособность;
- поддерживать будущие главы;
- не создавать ненужного технического долга;
- сохранять возможность замены ассетов;
- поддерживать сюжетную задумку;
- улучшать качество проекта.

Если между быстрым решением и архитектурно правильным решением нет существенной разницы по трудозатратам, выбирать архитектурно правильное.
